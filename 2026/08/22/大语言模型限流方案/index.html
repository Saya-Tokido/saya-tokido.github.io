大语言模型限流方案

1. 背景

限流采用分布式方案，基于 Redis 实现（参考 Higress 的做法）。限流粒度分两个维度：

  • 租户维度：QPM、TPM
  • 模型维度：QPM、TPM

2. 限流时机

  • QPM：请求进入、调用大模型之前扣减
  • TPM：调用大模型之后扣减

TPM 之所以后扣减，是因为请求前很难预知实际用量（Anthropic 协议里的 max_tokens 只能作为上限参考，不代表实际消耗）。

这意味着理论上存在”超卖”问题：如果配额接近打满时有多个请求并发在途，可能短暂超出配额。但实际业务流量相对平稳，可以接受。此外，限流策略是”等当前请求跑完”，而不是执行中途截断。

3. 限流算法选型

算法 时间复杂度 问题
固定窗口 O(1) 边界突刺，最坏情况可放行 2 倍流量，误差不可接受
令牌桶 O(1) 天然是”速率”模型，和产品要的”按分钟配额”语义不匹配
滑动窗口（滑动日志） O(n) 精确，但开销较大
双桶滑动窗口（滑动窗口计数器） O(1) 基于”上一桶请求均匀分布”的假设做插值，TPM 场景容易放大误差

最终选择滑动窗口（滑动日志）：牺牲一点性能换取精度，符合产品对分钟级配额的精确性要求。

4. 滑动窗口实现

QPM

  • 每次请求记录时间戳，维护一个 ZSet
  • 清理过期元素：O(n)
  • 读取 ZSet 长度即为当前窗口请求量：O(1)
  • 对比配额上限，判断是否放行

TPM

思路同 QPM，区别是额外维护一个计数器（而非直接取长度）：

  • 清理过期元素时，计数器同步扣减对应的 token 数
  • 总体时间复杂度 O(n)

5. 性能问题与优化

问题：QPM 达到 30000 时，单节点 CPU 占用 40%~50%，明显是单节点瓶颈。

优化：按 hashtag 拆分 Redis Key

  • 不同模型名称映射到不同 hashtag
  • 同一租户下不同模型也做拆分

拆分后仍有部分热点模型集中，但整体 CPU 压力已明显缓解。实测三分片下，负载最高节点的 CPU 占用降低约 50%。

未采用的方案：本地缓存 + 定时刷 Redis。虽然能进一步降压，但会引入额外误差，实现复杂度也更高，暂不考虑。

6. 配额体系：独占配额 + 共享配额

背景问题：

  • 很多租户申请了独占配额，但调用量很低甚至几乎不用，配额被闲置且不释放
  • 很多用户申请模型只是为了测试，对配额诉求没有明确概念，造成资源浪费

方案：

配额类型 适用场景 限流维度 特点
独占配额 核心业务 租户 + 模型 稳定性保障更好，无需和其他租户竞争
共享配额 非核心/测试场景 模型（全租户统一） 无需申请，直接用，多租户竞争同一配额池

效果与新问题：

  • 划分后，真正占用独占配额的租户数量减少，理论上分散度更好
  • 但实际情况是：独占配额租户的调用量往往更大、更恒定，热点效应反而更集中
  • 好处是热点范围收窄了——后续如果再遇到 CPU 瓶颈，可以针对性地对这些少数热点模型做专项优化（如引入本地缓存等手段）

7. 后续方向

  • 针对独占配额下的热点模型，评估本地缓存等更激进的降压方案
  • 持续观察共享配额池的竞争情况，避免测试类流量影响核心业务体验
